**評価の形**

- **評価セット**：質問・回答・参照（用語集のエントリと期待するふるまい）の組。演習は講師の 10 件（`data/eval/lec04_cases.jsonl`）、実装は自分で作った 10 件（`data/eval/my_cases.jsonl`）。
- **ラベル**：人が基準ごとに付けた合格（pass）か不合格（fail）。自分のラベル（`lectures/04/labels.jsonl`）と、講師のラベル（`lectures/04/reference/labels_instructor.jsonl`）がある。
- **rubric**：採点の基準を書いた文書（`data/eval/rubric.md`）。採点の LLM に、そのまま指示として渡す。
- **採点器**：rubric を与えた LLM。1 件ごとに、4 つの基準（根拠・範囲・ヒント・分かりやすさ）を pass・fail・unsure で判定する。「回の表示」は LLM に聞かずにコードで判定する。
- **要確認（unsure）**：採点器が、基準からは決められないとした判定。自動判定から外し、人が見る。

**数え方**

- **一致率 A**：`app/judge.py` の定義。判定が一致した件数 ÷ 比べた件数。LLM が unsure にした件は分母から外す。
- **coverage**：比べた件数 ÷ 全件数。
- **一致率 B**：unsure も不一致に数えた一致率。判定が一致した件数 ÷ 全件数。
- **常に pass**：すべてを pass と答える採点器の一致率。人のラベルの pass の件数 ÷ 全件数。
- **見逃し・過検出**：見逃しは、LLM が pass・人が fail。過検出は、LLM が fail・人が pass。
- **セル**：1 件 × 1 基準の判定。

**判定の出し方**

- **ツール出力**：配布の `app/judge.py` のやり方。判定の型（JSON スキーマ）を、関数の引数として LLM に渡し、LLM はその関数を呼ぶ形で答える。
- **構造化出力（NativeOutput）**：判定の型を、応答の形として LLM に渡し、LLM は JSON の文字列で答える。Gemini の公式文書は、構造化出力ではスキーマのキーの順に生成すると書いている。
- **propertyOrdering**：Gemini のスキーマで、プロパティを生成する順を明示する欄。

**揺れ**

- **変わった・傾向・揺れ**：同じセルを V0 と比べ、3 試行の中の pass・fail・unsure の回数の差の最大値で決める。差が 3 なら「変わった」、2 なら「傾向」、1 以下なら「揺れ」。

</details>

### 変えた設定

採点の設定を 1 か所ずつ変えた（V5 だけは複数の変更の束で、V6 と組で使う）。各条件で評価セット 10 件を 3 回ずつ採点し、自分のラベル（主）と講師のラベル（副）の両方と比べる。

| ID | 名前 | 変える場所 | 変更 | 比べる相手と、言えること |
|---|---|---|---|---|
| V0 | `baseline` | — | 講師の rubric、flash-lite、ツール出力、理由→判定（演習 STEP 2 と同じ） | 基準 |
| V1 | `step3_policy` | rubric | 演習 STEP 3 で、要確認の論点に方針を書き足した rubric | V0：方針を書き足した影響（演習の直す前・直した後を 3 試行で見る） |
| V2 | `model_flash` | モデル | `gemini-3.5-flash`（宿題の例と同じ） | V0：モデルの違い。思考の既定値の違いも含む（思考トークンを記録する） |
| V3 | `rubric_clarity` | rubric の文言 | 分かりやすさに「コードブロックを除いた本文が 450 字を超える場合は fail」を 1 行足す | V0：「簡潔」を数えられる形にした影響。同じ規則をコードでも数え、LLM が規則を正しく当てはめるかを見る |
| V4 | `order_schema` | 判定の順序 | `CriterionVerdict` のフィールドの順だけを verdict→reason にする（宿題の指示どおり。指示の文は変えない） | V0：宿題の指示どおりに順序を変えると判定が変わるか（生成の順は確かめられない） |

| V6 | `native_verdict_first` | 判定の順序 | V5 のスキーマの順だけを判定→理由にする | V5：順序だけの効果。全応答の生の JSON で、キーの順を確かめる |

<details><summary>条件をそろえるうえでの注意（1 か所ずつ、順序の操作の確かめ方、事前に決めた書き方）</summary>

- **1 か所ずつ**
  - `compare.py variants` で、各変種の V0 との差を表示して確かめた。数える項目は、モデル・rubric の本文・出力のしかた・順序・指示の末尾の 5 つ。
  - V1〜V4 は V0 と 1 点だけ、V6 は V5 と 1 点（順序）だけ違う。V5 は V0 と 3 点違う。テストでも固定した。
  - V0 の指示は、配布の `build_judge` が作る指示と一字一句同じ。V4 は `build_judge` の Agent に、出力の型だけを差し替えて渡す（`run_sync(output_type=...)`）ので、指示は V0 と同じになる。
- **順序の操作の確かめ方**（pydantic-ai 2.57.0 のソースと、Google の公式文書で確かめた）
  - 配布コードはツール出力で、判定の型を関数の引数として送る。
    - 関数の引数がスキーマの順に生成される、という公式の記述は無い。
    - 応答の引数は Struct（map）なので、受け取った dict の順は生成の順の証拠にならない。
    - そのため V4 は「宿題の指示どおりにやったとき、何が起きるか」を見る条件で、生成の順そのものは確かめられない。
  - 構造化出力（NativeOutput。要求の `responseJsonSchema`）は、スキーマのキーの順に生成すると公式に書かれている。
    - V5・V6 は propertyOrdering も付けた。
    - 全応答で、モデルが書いた JSON の文字列のキーの順を確かめる。
  - 「理由→判定」は、型のほかに 3 か所に書いてある：型の docstring（スキーマの説明として送られる）、`build_judge` が足す「出力の形式」の文、rubric の「先に理由を書いてから判定を決める」。
    - V4 はこの 3 か所を残した。指示と型が食い違う条件になる。
    - V5・V6 は、rubric の 1 文と「出力の形式」の文を外し、順序に触れない文に替えた。
- **事前に決めた書き方**（結果を見る前に決めた）
  - V5・V6 のキーの順が全件、条件どおりだった：V6 と V5 の差を、順序の効果として読む。
  - 一部だけ条件どおりだった：条件どおりの応答だけで集計し、外れた件数を書く。
  - NativeOutput が使えなかった（400 など）：順序の効果は検証できなかったと書き、V4 だけで報告する。
  - V4 の判定が V0 と揺れの範囲で同じだった：「型を入れ替えても変わらなかった（ツール出力では、順序が効く保証が無い）」と書く。
  - 思考トークンは記録するだけで、モデルが内部でどの順に考えたかは推定しない。
- **V3 の閾値**
  - 450 字は、講座の偽モデル（`--model test`）と同じ値で、こちらが回答を見て決めた値ではない。ただし、講師がこの 10 件を見て決めた可能性はある。

### 仮説（実行前に記録）

2026-11-16、自分のラベルを commit した後、LLM の採点を始める前に記録した。

自分のラベルの fail は、根拠が #10、範囲が #08、ヒントが #06、分かりやすさが #04 の各 1 件、回の表示が #02・#07・#09 の 3 件。そのため「常に pass」の一致率は、LLM が判定する 4 基準が 9/10、回の表示が 7/10、総合が 4/10 になる。

1. **回の表示（コード）**：どの条件・試行でも 10/10 になる。コードは、自分のラベルと同じ 3 件（#02・#07・#09）を fail にし、試行で変わらないから。
2. **V0 の要確認**：#05 の根拠に集中する（3 試行中 2 回以上）。ほかの要確認は、1 試行あたり 0〜1 件。
   - rubric の「まだ決めていないこと」に、そのまま書いてある論点だから。
   - ただし講師は「採点のモデルは、基準に書いていない論点でも pass / fail を決めてしまう」と書いているので、1 回以上 pass になるかもしれない。
3. **V0 の不一致**：1 試行あたり 0〜2 件。出るとしたら次の 2 つ。
   - #08 の根拠：参照の用語集が空なのに、回答は用語集の内容を並べている。LLM はそれを「参照にない事柄の断定」と読んで、fail か unsure にする（人は pass）。
   - #06 の分かりやすさ：長いコードを、読みやすさの判定に持ち込む。
   - 分かりやすさの一致率は、演習の説明（「分かりやすさの一致率が低い」）ほどは下がらない。講師が #04・#06・#08 の分かりやすさに合わせて rubric を直したから（標本内）。
4. **V0 の揺れ**：試行によって判定が変わるセルは、LLM が判定する 40 セルのうち 1〜3 個。
   - temperature 0 が効いていれば 0 個に近くなるはず。
   - 応答ヘッダに temperature の非推奨の警告が出るか（＝ temperature が無視されているか）は分からない。記録で確かめる。
5. **V1（STEP 3 の方針）**
   - 方針を pass にしたら、#05 の根拠は 3/3 で pass になる（V0 から「変わった」）。要確認は 0 件になり、根拠の一致率 A の分母は 10 になる。
   - 方針を fail にしたら、3/3 で fail になり、凍結した自分のラベル（pass）とは不一致になる。
   - どちらでも、ほかのセルは揺れの範囲にとどまる。
6. **V2（gemini-3.5-flash）**
   - #05 の要確認は 3/3 で出る。flash-lite より、rubric の「まだ決めていないこと」に従うから。
   - 不一致は V0 と同じか、少ない。
   - 思考トークンは flash-lite の数倍になり（既定の思考の深さが違う）、1 件あたりの時間も長くなる。
7. **V3（450 字の規則）**
   - #04（516 字）の分かりやすさは 3/3 で fail（V0 と同じ）。
   - #08（425 字）は、LLM が字数を数え損ねて、3 試行中 1 回以上 fail にする（コードの判定は pass）。LLM は日本語の字数を正確に数えられないから。
8. **V4（型の順だけ入れ替え）**：V0 と比べて「変わった」セルは無く、差は揺れの範囲にとどまる。指示の文は「理由を先に」のままで、ツール出力では生成の順がスキーマに従う保証も無いから。
9. **V5・V6（構造化出力）**
   - キーの順は、どちらも 30 件中 28 件以上が条件どおりになる（公式文書のとおり、スキーマの順に生成する）。
   - V6（判定が先）は、V5 より #05 の要確認が少ない。理由を書く前に、pass か fail に決めてしまうから。
   - ほかのセルは揺れの範囲にとどまる。
10. **「常に pass」との比較**
    - LLM が判定する 4 基準は、どの条件でも一致率 A が 9/10 前後になり、「常に pass」（9/10）と見分けがつかない。
    - 条件の違いは、fail の 1 件を当てたか（見逃し）と、pass を落としたか（過検出）でしか見えない。
