### 1. ファインチューニング（第2回）と構造化出力（第3回）の使い分け

実務で形式を指定したい場合、まずはどちらを検討すべきでしょうか。資料では以下のように整理されています。

* **実務での優先順位：**
  形だけを確実に守らせたい場合、まずはプロンプトでの指示や API の機能（構造化出力）を使うことが先決とされています（第2回・PDF p.53）。
* **構造化出力を使う場面（第3回）：**
  文書からの項目抽出や、選択肢からの分類・判定、あるいはツールを呼び出す際など、明確に決まったスキーマ（項目と型の決まり）に沿ってデータを返させたい場合に利用します（第3回・PDF p.34）。
* **ファインチューニングを使う場面（第2回）：**
  形式だけでなく、「口頭の丁寧さ」「根拠の示し方」「手順の守り方」といった、書式だけでは縛り切れないモデル全体の「振る舞い」そのものを直したい場合に、少量の手本を用いて調整（SFTなど）を行います（第2回・PDF p.23, 46, 54）。

まずは API の構造化出力やプロンプトで対応できないか検討し、それでも振る舞いに癖が出てしまう場合にファインチューニングを検討するのが基本的なアプローチになります。

### 2. 構造化出力はどうやって形式を守らせているのか？

構造化出力が確実に形式を守れる仕組みの背景には、**「制約付きデコーディング」**という技術があります（第3回・PDF p.35）。

* **仕組みの考え方：**
  LLM がテキストを生成する際、次に続くトークン（文字や単語の断片）を1つずつ確率的に選びながら出力していきます（第3回・PDF p.35）。
* **形式崩れを防ぐアプローチ：**
  構造化出力（APIの `json_schema` 指定や `strict: true` など）では、事前に定義されたスキーマを確認し、**「次に生成するトークンとしてスキーマの形式に合わない候補」をその都度、候補から強制的に除外**します（第3回・PDF p.34, 35, 62）。
* **結果：**
  スキーマに反する文字やフォーマットの崩れがそもそも生成されない仕組みになっているため、高い確率で指定した JSON 形式などの出力を得ることができます（第3回・PDF p.35）。
